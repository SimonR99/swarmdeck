# Known issues

| Area | Limitation, trap, and mitigation |
|---|---|
| Python environment & GTSAM segfault | `slam/` is strictly pinned to Python 3.12 and `numpy<2`. GTSAM 4.2.2 segfaults with bare SIGSEGV under NumPy 2.x (Python 3.13). Never combine `server/.venv` (3.13) and `slam/.venv` (3.12). |
| GTSAM tangent vector order | Information matrices and tangent vectors in `slam/` are 6x6 **rotation first** ($\omega_x, \omega_y, \omega_z, v_x, v_y, v_z$). Ordering mistakes fail silently without errors; guarded by tests in `slam/tests/`. |
| Transform naming direction | Every transform `T_a_b` maps points from frame `b` to frame `a` ($p_a = T_{a\_b} \cdot p_b$). |
| PCM clique threshold | `min_pcm_clique_size = 2`: trajectory merging requires at least two corroborating inter-robot loop closures. A single drive-by overlap will deliberately remain unmerged until re-visited. |
| Motion skew at turn rates | In simulation, spinning lidar clouds have no per-point timestamps and distort during fast yaw (> 8 deg/s), causing GICP to lock onto warped structure. `keyframe_producer.py` drops frames above `DEFAULT_MAX_YAW_RATE = 0.14 rad/s`. |
| Exploration bootstrap vs operator goals | `explore.py` and Nav2's `velocity_smoother` publish to the same `<ns>/cmd_vel`. While both command one robot it receives interleaved, contradictory velocities and follows neither, which looks like a robot ignoring its planned path or a broken transform. Exploration now watches each robot's `navigate_to_pose` status and stops commanding any robot with an accepted or executing goal (logged as `yielding to an operator goal`). Note that `EXPLORE_SECONDS` is WALL-CLOCK by design, so a low real-time factor widens the window during which an operator may issue a goal without shortening it; `EXPLORE_SECONDS=0` disables the bootstrap. |
| Simulation reset boundary | The `reset` capability is strictly simulation-only (`adapter_sim`, `mock_adapter`). Hardware adapters (`adapter_ros1`, `adapter_ros2`) must never advertise or implement `reset`. |
| Auto map registration overhead | In `merge_mode: auto`, grid correlation costs ~2.44 s per ingest if reference robot is missing. Use `merge_mode: graph` (default in `configs/4robot.yaml` and `hardware_fleet.yaml`) for trajectory-based merging. |
| Collaborative merge (legacy cslam) | RTAB-Map grids and Swarm-SLAM trajectories disagree by 11–16 m. Treat `merge_mode: cslam` as a legacy diagnostic; use `merge_mode: graph` for production. |
| 3D simulation | `GRID_3D=true` preserves cloud height but roughly halves simulation speed. Leave it off unless the 3D structure is needed. |
| DLIO in Gazebo | Simulated clouds lack per-point timestamps, so DLIO cannot demonstrate de-skewing. Do not extrapolate its Gazebo result to hardware. |
| Odometry covariance | Legacy Gazebo backend only. The EKF is tuned for its current measurement model. Enabling `FUSE_COVARIANCE=true` requires retuning process noise. |
| Gazebo lidar ring parity | Legacy Gazebo backend. Height-filtered planar mapping requires 1 or an odd number of vertical rings (e.g., 33); even counts leave no beam at elevation 0 and distant walls truncate. |
| Fast DDS drops point clouds silently | A 17-ring revolution is ~630 KB and Fast DDS sizes its UDP socket buffer from `net.core.rmem_max`, 208 KB by default, so a single message does not fit, the fragments overflow, and it is never reassembled. The publisher reports success and nothing logs an error: the only symptom is Ultra-Fusion appearing to diverge. Measured upstream at 87% loss, presenting as 47% drift. `fastdds_large.xml` asks for 7 MB buffers, and the ceiling on that is a **host** setting: `sudo sysctl -w net.core.rmem_max=8388608`. It cannot be set from the container (the sysctl is global, not per-netns, and Docker refuses to create a container that asks); `run_uf.sh` reads it at startup and warns. Check `arrivals{}` in the estimator's log before touching any tuning parameter. |
| Ultra-Fusion is a third-party binary | It comes from one Docker Hub tag (`maotiandocker/ultrafusion-ros2:0.2.0`; the documented `0.2.1` does not exist) plus a GitHub release `.deb` whose declared dependencies that image does not carry. Both are worked around in `deploy/docker/ultrafusion/Dockerfile`; both are upstream artifacts that can move. |
| ARGoS runs in lockstep with the estimator | The `external_estimator` exchange blocks, so the simulation's real-time factor is bounded by Ultra-Fusion. That is deliberate (nothing is dropped however slow the estimator is), but it means a slow estimator shows up as a slow simulation rather than as missing data. |
| Photorealism entity descriptors | An entity type with no `<type>.visual.xml` in the asset search path is skipped by the renderer, matched by exact name. The robot is then invisible in RGB, depth and segmentation *and* to every other robot's lidar, which raytraces the render scene. The only sign is one `[INFO] Photorealism: no visual model for entity type` line. `make visual-test` catches it. |
| Exposure and illuminance are one setting | The photorealism medium is physically based, so `<sun intensity>` and `<exposure>` have to agree: EV = log2(N^2/t * 100/S). Pairing 70 klux with EV 10.9 returns a white frame with the geometry burned out of it, while depth and segmentation stay perfect, so nothing downstream notices the photograph is unusable. |
| ARGoS lidar ring parity | Same rule as Gazebo, different mechanism: ARGoS spreads `rings` evenly over `vertical_fov`, so an even count leaves no ring at elevation 0 and `cloud_to_scan`'s `slice` mode selects nothing at range. `configs/*.yaml` use 17 rings over +/-15 deg, which is VLP-16 geometry plus a horizontal ring. |
| Unix socket path length | The three simulation containers share `/run/swarmdeck`, and it is short on purpose: a Unix socket path over 107 bytes fails to bind with "AF_UNIX path too long", named in whichever process binds first and not in the one that configured it. |
| Simulated detection targets are placeholders | The five models in `argos/assets/props/` are procedural, built from the catalog's own prompt descriptions rather than photographed objects. Recall against them is not evidence about the hardware catalog; re-run `tests/perception/test_catalog_recall.py` on real fixtures before drawing conclusions. |
| Detection prompts | YOLOE results depend on prompt and hardware domain. Validate catalog changes with `tests/perception/test_catalog_recall.py` inside the detector container. |
| Hardware frames | Camera/lidar extrinsics must be measured. Botman intentionally refuses deployment without its six OAK mount values. |
| ROS domains | Keep each hardware stack on its documented `ROS_DOMAIN_ID` unless the entire graph is reconfigured together. |
| Remote access | SwarmDeck has no authentication. Put an authenticating proxy in front of any hardware-facing deployment. |
